# Releasing

How a version of Limpide is published. A release starts only on the owner's own "push" or "release" ([CLAUDE.md](../CLAUDE.md)). This page is the one home of the release rules: an ADR records why a rule was chosen, and an issue or another document points here rather than restating it ([ADR-0016](adr/0016-the-release-steps-are-the-one-home-of-the-release-rules.md)). Each release is a push, in this order; a version is published only once it is live:

1. `git fetch`, and if `main` is behind `origin/main`, replay it on top (`git rebase origin/main`, dropping any commit GitHub already has under another hash), so the suite below tests what ships. Another session may have pushed meanwhile.
2. **A release that carries issue work** (a feature, a fix, a refactor that changes nothing visible) first gets a code review: the code-review skill over everything since the last tag. Fix the bugs it finds; send the rest to the inbox.
3. **The local suite:** `npx tsc`, `npm run lint` and `npx vitest run` green, and the Playwright specs the release's changes touch (`npm run test:changed` finds them). All of Playwright runs on GitHub, in parallel jobs ([ADR-0015](adr/0015-ci-runs-the-end-to-end-tests-before-a-deploy.md)).
4. The version: patch by default, minor for new visible features, major only on the owner's word (`npm version X.Y.Z --no-git-tag-version`), and its line in `docs/issues/25-releases.md`. With it, **the shipped issues' Status lines:** each issue the release carries, its Status line saying "merged into main, not yet released", says "merged into main, released in X.Y.Z" instead (`grep -l "not yet released" docs/issues/*.md` finds them). Commit them together as `Issue 25: version X.Y.Z` (issue 25 is the release log).
5. **The branch run green:** push the commit to its release branch, not to `main`: `git push --force-with-lease origin main:release/X.Y.Z` (the lease lets a release started again at step 1 replace the branch's old commit). GitHub runs the same build and the whole suite as for `main`, on its Linux and its fonts, which the layout tests are measured in, and deploys nothing (about 6 minutes). Its run shows a few seconds after the push: `until id=$(gh run list --branch release/X.Y.Z --commit "$(git rev-parse main)" --limit 1 --json databaseId --jq '.[0].databaseId // empty') && [ -n "$id" ]; do sleep 5; done; gh run watch "$id" --exit-status`. If it is red, fix it, commit, and push the branch again under the same version (its release-log line says what the fix added).
6. **The checks on words**, which can run while the branch run does, each over everything since the last tag, with the briefs of issue 42's reviewers 12 to 14 (the opening lines of their [first reports](reviews/2026-10-30/)):
   - **A release that adds or changes Preset or tip words** (a Preset's description, a tooltip): the fact-checker renders them through the engine and tests every claim they make, and checks a new or changed History line against its sources in [History's sources](research/134-history-in-the-tooltips.md) (issue 134); the ear stand-in renders each new or changed Preset for its level, clicks, clipping, harshness and fold-back.
   - **A release that carries issue work:** the ripple hunter finds every test, tip, description and doc still stating what the release made untrue.

   Fix what they find, or answer it with a line in the inbox; a fix is committed and goes through step 5 again.
7. **Then `main`:** `git push origin main`, the commit the branch run tested: a push to `main` deploys the site. If GitHub refuses it because `main` moved meanwhile, start again at step 1.
8. When the deploy run is green (about 6 minutes): an annotated tag `vX.Y.Z` on that commit, `git push origin vX.Y.Z`, and `gh release create vX.Y.Z --title "Limpide X.Y.Z"` with the version's release-log line as its notes: every Release is titled in that one form (issue 111). The release branch has done its work: `git push origin --delete release/X.Y.Z`.
9. The statistics, after the push: `npm run stats` measures the release's size, quality and performance and writes its row into [statistics.md](statistics.md) and the README's summary (issue 84). It runs the whole suite again, with coverage, then the page load and the running app, in about an hour: on a quiet machine, with no other session's tests running, since the timings count. It ends with an error if a test, the types or the lint failed. Its row is committed, and goes out with the next push.
10. If the deploy fails, fix it as in step 5, through the branch and then `main`: a failed attempt costs no version number. A re-run of the same commit needs no push.
