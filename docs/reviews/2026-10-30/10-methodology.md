## First impression

"Last time I left three findings: no review gate, mutable ADRs, and commits that don't name their issue. Two days later there are two process ADRs (0010, 0012), a retro, commit hooks with their own unit tests, and a review run before every release. So the method can take criticism, and fast. What I want to know now is whether the new rules hold at 110 commits a day, and where the work goes when it doesn't fit them."

## What worked

- **The method took its review and changed within a day.** It recorded why (ADR-0010, ADR-0012) and said who decided ("the owner, grilling of issue 56"). A process change made as a dated, owned decision is rarer than it should be on human teams.
- **Process rules as tested code.** `scripts/commitChecks.ts` has unit tests and runs in hooks. It is the same idea as the design-principles ratchet, applied to the process itself: every subject since ADR-0010 names its issue or says there is none, and one is a character over 72.
- **A real review gate.** Run every release, fixes before the push, the rest triaged through the inbox, and it finds ticked boxes that aren't true.
- **Spec, then build, as separate commits.** "Issue 74: …, grilled" (`0138a93`), then "Issue 74: one law per LFO Destination…" (`4f864f3`). The spec is in the history before the code, with numbered Decisions, each saying who decided: 109 "decided by the owner", 50 "Claude's call, open to the owner".
- **Triage states that answer queries.** All 10 open issues carry one state and one category. The three `ready-for-agent` ones have Agent Briefs with no file paths, as ADR-0012 asks.
- **Saying no is now recorded.** Dropped, `.out-of-scope/`, and the owner withdrawing an idea once shown the cost (double-click to zero).

## Where they got stuck

- **Two roads, one of them unsigned.** The issue road is now exemplary. The done-at-once road carries 45% of source commits, including features, and leaves no mark on the issues whose decisions it overturns (`9e34d4e` vs issues 44 and 82).
- **Process text drifts like product text did.** The code-review rule disagrees with itself across ADR-0010, `docs/releasing.md`, issue 25 and issue 42. Amended ADRs don't point to what amends them.
- **The same release failure five times, no root cause.** Mac-green, Linux-red. The retro fixed four other things. A Lean reader would ask why the Linux-fonts failure had no 5 Whys.
- **Bookkeeping is a large share of the history.** More than half the commits since ADR-0010 touch the inbox. With an agent it costs little to write, but it costs a reader time. `git log` is now a change-request log at one-minute grain, and the Triaged log is the real decision register for half the features.

## Would they…

- **Adopt it for a team:** closer than last time, still no. Who-decided metadata, frozen ADRs and a review gate are all in place. What's still missing for a team: a done-at-once threshold (what size of change must get an issue), and a single home for each process rule.
- **Recommend it to a solo developer with an agent:** yes, more strongly than before. The process fixed itself from a review in a day and enforces itself with tested hooks.
- **Teach it:** yes. The trace from story 92 to issue 89 to its test, the grilled-then-built pairs (issues 73–79), and `commitChecks.ts` are ready-made slides. `9e34d4e` against issue 82 is the cautionary one.

## Since 1.8.1

All three findings from 2026-10-26 were acted on. **Review gate:** the code-review skill now runs before every release that carries issue work. It has run eight times, and it fixed real gaps before the push. Refactoring shows up as its own issues (55, 70, 73–79), and `App.tsx` went from 963 lines to 684. **ADRs:** all 14 have Status, Date and Decided by, none has been edited since being accepted, and reversals and amendments are new ADRs (0011, 0014). What's left: the amended ADR's Status line doesn't point forward. **Traceability:** 232 of 233 subjects name an issue or say there is none, and the hook enforces it. Inbox lines are committed in the owner's words before triage. Stories 90–96 and their issues cite each other. What's left: the "No issue" road, which now carries the untraced features the 1.1.0 run used to. Also new since then: a retro, ADR-0012's triage states and Agent Briefs, and CI running every suite (issue 54). Still not visible: test-first, and a sustainable pace (44 commits between midnight and 3 am).

## Three findings, ranked

1. "Done at once" changes skip the issues they overturn. Since ADR-0010, 47 of 104 source-changing commits are `No issue:`, features among them (17 Presets `497633d`, an Env Timeline setting `12b4887`, the header relayout `9e34d4e`). `9e34d4e` reversed issue 82's decision 4 and falsified issue 44's ticked "DOM order = screen order" without touching either, so 82 still waits on the owner. Write the "Since then" rule into `docs/agents/issue-tracker.md`, and give a change that alters an issue's decision, a setting, or a batch of Presets an issue number.
2. The pre-push gate isn't the deploy gate. 7 of 14 release pushes since 1.9.0 went red on CI first, 5 of them for the same Linux-fonts layout failure that was green on the Mac. `v1.12.2` and `v1.12.3` tag undeployed commits and `v1.12.4` tags `aca10cb`, whose run failed. The retro (`26dd7ea`) left the cause alone. Make releasing step 3 run the layout e2e in Playwright's Linux image (the inbox's own idea), and triage that idea first.
3. Process rules drift across their homes. The retro moved "code review before minor releases" to "every release with issue work" in `docs/releasing.md` only. ADR-0010 point 5 still says "Patch releases skip it", issues 42 and 25 still say minor-only, and issue 25 points to steps in `CLAUDE.md` that moved out. ADR-0006 and 0013 carry no "amended by 0011 / 0014" in their Status lines. Record retro decisions as an ADR that supersedes in part, and let an amended ADR's Status line name its amendment.
