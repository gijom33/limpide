# Persona review 8: the open-source expert, sceptical of AI

Laptop, 30 minutes, 2026-10-26. The repository as a visitor sees it on GitHub (https://github.com/gijom33/limpide), a fresh `git clone` from GitHub into a scratch folder (Node 25.8.2, npm 11.11.1), `gh` for what only GitHub shows. Nothing in the repository was changed; the mutation experiments below ran in the scratch clone and were reverted there.

## First impression

"MIT licence, detected by GitHub. A product README with a live link, a run-locally table, and a 'How it's built' section pointing at a glossary, ADRs and numbered issues. 206 commits in six days by one person, every one co-authored by Claude. So it's an agent-built app with a lot of paperwork. The paperwork is either the best thing here or a smoke screen. Let's see if it builds, and whether the tests would notice if I broke something."

## What they tried, in order

1. **Community profile.** `gh api repos/gijom33/limpide/community/profile` gives `"health_percentage":42`: README and MIT licence are there; `code_of_conduct`, `contributing`, `issue_template` and `pull_request_template` are all `null`. Issues are enabled (0 opened), Discussions off, one branch (`main`), not protected (`gh api …/branches/main/protection` → 404), 0 tags, 0 Releases, 0 pull requests ever. `docs/inbox.md` line 3 says "GitHub Issues stay for visitors", but nothing on GitHub tells a visitor what to put in one.
2. **Build as a stranger.** `git clone`, `npm ci` → "added 68 packages … found 0 vulnerabilities" in 0.8 s. `npm run build` (`tsc && vite build`) → green in 1.8 s, a 383 kB bundle (122 kB gzip). No surprises.
3. **`npm test`.** It isn't in the README's table, but it's the first thing I type. It runs both Vitest projects, unit and engine (`vite.config.ts` lines 41–62): 45 files, **548 tests, all green in 33 s**. Chromium was already in my Playwright cache; on a clean machine the engine half needs `npx playwright install chromium` first, which the README does say, one line under the table.
4. **E2E.** `npx playwright test` → **579 passed, 1 failed, 6 skipped in 4.4 min**, Chromium and WebKit. The failure was `[webkit] e2e/oscTabs.spec.ts:76 › Pulse Width sits in the same place … (1710px)` with "Error: Cannot find parent object browser@… to create debugger@…", a Playwright/WebKit internal error, not an assertion. I'm calling it a flake of the harness, not of the app. The 6 skips are honest and explained (`test.skip(browserName !== 'chromium', 'touch input through the DevTools protocol')`, `e2e/knob.spec.ts:133`).
5. **Dependencies.** `package.json`: 2 runtime deps (`react`, `react-dom`), 10 dev deps, 176 lines in `npm ls --all`. `npm audit` → 0 vulnerabilities. `npm outdated` → only `@vitest/browser-playwright` 4.1.12 vs 5.0.5 (a major). TypeScript 7, Vite 8, React 19.3: current. No audio library at all. This is the leanest dependency tree I've seen on a React app this year.
6. **Read the tests, then try to break the code.** I read `src/modulation/lfo.test.ts` and `src/engine/synthEngine.browser.test.ts`. The engine tests render real audio in an `OfflineAudioContext` and measure harmonics in dB, with *control cases* ("hears hiss when there is some: a little Noise in the Mixer is caught (control case)", line 53). That is someone who knows a test can pass vacuously. Then I mutated the code in my clone:
   - `src/modulation/envelope.ts` line 53: release time constant computed from `decay` instead of `release` → **caught** (1 unit test fails).
   - `src/patch/taper.ts` line 13: drop `clamp01` → **caught** (1 fails).
   - `src/midi/parser.ts` line 58: MIDI channel off by one → **caught** (11 fail).
   - `src/ui/App.tsx` line 417: swap the MIDI "Next Preset"/"Previous Preset" action (`? 1 : -1` → `? -1 : 1`) → **survived everything**: all 548 Vitest tests and all 293 Chromium e2e tests green. No test drives a mapped Preset arrow through the app. The pure modules are well guarded; the glue isn't.
7. **Read the glue.** `src/ui/App.tsx` is 963 lines, and `App()` alone runs from line 125 to the end: 27 `useState`, 17 `useRef`, 19 `useEffect` in one function. Six refs mirror state by hand on every render (`stopDemoRef.current = stopDemo` line 153, `octaveRef` 306, `heldRef` 315, `pressHoldRef` 326, `patchRef` 371, `patchNameRef` 374). Things are used far above where they're declared: `playDemo` reads `session` (line 165) and `patchRef` (line 170), declared at lines 291 and 370. The same engine adapter (`noteOn: (note, velocity, at) => engine.noteOn(note, velocity, at)`, plus `noteOff`, `release`, `now`, `voices`) is written out three times, for the Demo (line 190), the Song (232) and the Hold rhythm (339). `git log` shows App.tsx touched in 70 of 206 commits and `src/styles.css` (1,030 lines, 20 distinct `@media` queries with breakpoints at 600/601, 860/861, 919, 960, 1299 px) in 98. Any outside PR will conflict with whatever the owner's agent did that afternoon.
8. **Looked for the marks of unreviewed AI output in the code.**
   - Three `// eslint-disable-line react-hooks/exhaustive-deps` (`src/ui/App.tsx` 286 and 353, `src/ui/SectionStrip.tsx` 135), but ESLint isn't installed and never was (`git log -S'"eslint' -- package.json` is empty). The comments silence a linter nobody runs. There is no linter or formatter config at all (no ESLint, Prettier, Biome, EditorConfig).
   - What a linter would have caught: `src/ui/App.tsx` imports from `'../patch/presets'` twice (lines 15 and 25).
   - A code comment repeats the docs drift the AI expert found: `src/engine/synthEngine.ts` line 15 says the Amp Tap follows "the newest Note's alone (the default, ADR-0007)". The engine's own default is indeed `'newest'` (line 533), but the app starts on `tapSource: 'all'` (`src/viewers/viewerState.ts` line 27). Two defaults in two places, and the comment names the one users never see.
   - Otherwise the code is better than I expected. `strict`, `noUnusedLocals` and `noUnusedParameters` are on (`tsconfig.json`); there is not one `as any`, `@ts-ignore` or `@ts-expect-error` in `src/` or `e2e/`; no TODO/FIXME; comments explain *why* and cite ADRs rather than narrating the code. The whole codebase uses the words in `CONTEXT.md` consistently, which is unusual. Comment density is modest, not the wall of AI boilerplate I expected.
9. **E2E test style.** 36 `page.waitForTimeout` calls across 10 specs (e.g. `e2e/demo.spec.ts` line 105: `waitForTimeout(4500); // past the Amp's Decay starting to move`). Some are inherent to testing a timed Demo, but fixed sleeps are what made the timing tests flaky; `docs/inbox.md` logs three rounds of flaky-test fixes on 2026-10-25 and 26. Pixel assertions like `expect(h.piano.height).toBe(64)` (`e2e/header.spec.ts` line 66) pin today's layout; an outside contributor touching CSS will fail tests whose intent they can't guess.
10. **Commit size and review.** The biggest commits touch 1,653 lines (`2d40e62`, MIDI Learn), 985 (`5935587`) and ~900 (`9c1535f`, `80bde59`) of src and e2e. About 27,000 insertions in six days, all pushed straight to `main`, no pull requests, no branch protection. The issues prove the owner *decided* things ("decided by the owner on 2026-10-26"); nothing in the repo shows anyone *read the diffs*. `docs/issues/42-reviews.md` plans the first whole-codebase code review, unchecked. To be fair, that is the next step they've written down.

On the AI expert's findings: I agree the README hides how it was built and that CI should run the browser tests (they pass locally, so there's no excuse). The docs drift is real, and I found the same drift in a code comment (above). The long commit subjects bother me less than the commit *sizes*.

## What worked

- **Build and test from a cold clone, first try.** `npm ci`, `npm run build`, `npm test` all green; 579 of 580 e2e passing on two engines. That beats most human-written hobby projects I review.
- **Dependencies:** two runtime deps, no audio library, 0 vulnerabilities, everything current but one dev major.
- **The domain tests are real.** Offline audio rendering measured against Fourier series, control cases that prove the measurement can fail, and three out of three mutations in pure modules caught.
- **Types are honest:** strict mode, no `any`, no suppressed type errors.
- **Attribution is honest:** every commit carries `Co-Authored-By: Claude`, and the ADRs record decisions the owner reversed. I'd rather see that than a README claiming "hand-crafted".

## Where they got stuck or gave up

- **How to contribute.** No CONTRIBUTING, no issue or PR template, no code of conduct (community profile 42 %). The project's real workflow (PRD → `docs/issues` → `docs/inbox.md`) is private by design ("GitHub Issues stay for visitors"), so I can't tell whether a PR is welcome, whether I should open an issue first, or which of the numbered markdown issues are open. I'd give up here as a contributor.
- **Changing the UI.** Any feature touches `App.tsx` (one 840-line component) and `styles.css` (20 media queries). With no linter or formatter, my editor's defaults would reformat things, and the pixel-exact e2e tests would fail for reasons I'd have to reverse-engineer from issue files.
- **Trusting the glue.** The MIDI Preset arrows could run backwards and no test would notice. That's exactly the layer an agent rewrites most often (70 commits) and the least guarded.

## The Hacker News comment

> I went in expecting slop and came out mostly impressed, with caveats. Fresh clone, `npm ci && npm run build && npm test`: green, 548 tests in 33 s, 579/580 Playwright tests across Chromium and WebKit, two runtime deps, zero audit findings. The DSP tests render real audio offline and check harmonics against the Fourier series, with control cases, and three mutations I made in the pure modules were all caught. That's better testing than most hand-written side projects. The AI shows in the glue: a 963-line `App.tsx` with 27 useStates and 17 hand-synced refs, touched in a third of all commits; `eslint-disable` comments for an ESLint that was never installed; a duplicate import a linter would catch; docs and even a code comment that disagree about a default. I flipped the MIDI next/previous-preset wiring and the whole suite stayed green. 27k lines in six days pushed straight to main, no PRs, no CONTRIBUTING, no templates. It's honest about the AI (co-author trailer on every commit), and the ADR/issue trail is a genuinely good record of who decided what. But it's a one-person-plus-agent project, not yet a project you can contribute to.

## Would they…

- **Contribute:** no, not yet. There's no CONTRIBUTING or template, the workflow lives in markdown issues outside GitHub, there's no linter or formatter, and every UI change goes through one 963-line component that the owner's agent changes several times a day. A PR would be stale by evening.
- **Depend on it:** no, and it isn't meant to be depended on. It's an app (`"private": true` in `package.json`), not a library, with no tags or Releases to pin. The pure modules (`src/modulation`, `src/patch/taper.ts`, `src/midi/parser.ts`) are good enough that I'd copy them under the MIT licence rather than depend on them.
- **Star it:** yes. It builds clean, the tests have teeth, and the dependency list is two lines. That earns a star even from me.
- **Recommend it as an example of AI-assisted open source:** yes for the *process* and the *testing of pure logic*, with a stated caveat about the UI layer and review. I'd point people at `src/engine/synthEngine.browser.test.ts` and the ADRs, and warn them off `src/ui/App.tsx` as the thing to avoid. It would become an unreserved yes with a CONTRIBUTING file, a linter in CI, and the browser tests in CI.

## Three findings, ranked

1. `src/ui/App.tsx` (963 lines; `App()` from line 125 has 27 `useState`, 17 `useRef`, 19 `useEffect`, six hand-synced refs, the engine adapter written out three times at lines 190, 232 and 339; touched in 70 of 206 commits) is the least-tested, most-churned code: swapping the MIDI Next/Previous Preset action at line 417 survives all 548 Vitest and 293 Chromium e2e tests. Split it into hooks per concern (Demo/Song, MIDI surface, Quick Setup, Hold) and test the MIDI actions.
2. No contributor on-ramp: GitHub community profile 42 % (`gh api repos/gijom33/limpide/community/profile`: no CONTRIBUTING, issue or PR template, code of conduct), `main` unprotected, no PRs ever, and `docs/inbox.md` line 3 sends visitors to GitHub Issues without saying what's welcome. Add a short CONTRIBUTING (the PRD/issue/ADR workflow, `npm test` plus `npx playwright install chromium`, whether PRs are accepted) and a bug-report template.
3. No linter or formatter, though the code assumes one: `// eslint-disable-line react-hooks/exhaustive-deps` at `src/ui/App.tsx` 286 and 353 and `src/ui/SectionStrip.tsx` 135 silence an ESLint that was never installed, and a duplicate import from `'../patch/presets'` (App.tsx lines 15 and 25) slipped through. Add ESLint with `react-hooks` (and Prettier or Biome) and run it in CI. Fix the stale comment at `src/engine/synthEngine.ts` line 15 ("the newest Note's alone (the default…)" while `src/viewers/viewerState.ts` line 27 defaults to `'all'`) at the same time.
